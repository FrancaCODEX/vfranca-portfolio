## The project

**CritPlay** is a gaming community: log what you're playing, rate it, publish reviews, follow people and find what to play next. The Java backend and the web UI run as a single application.

![CritPlay](/projects/critplay-destaque.webp)

## Features

- **Catalog** with search and filters, admin editing and imports from the **RAWG API**, one by one or in batches of 500, 1,000 and 2,000 games
- **Game diary** with progress, half-star ratings (0.5 to 5), reviews and dates, plus a library by status, favorites, wishlist and lists
- **Social:** profiles with avatar and banner (GIFs included), up to four featured games, followers, friendships, an **activity feed** and review likes
- **PC prices** via the GG.deals API
- **Administration:** accounts and roles, suspension, reports, review moderation, blocking and cleanup of unused images
- Session login, password change and email recovery (SMTP or Resend)

## Architecture

A modular monolith: static UI and REST API in the same Java process.

```text
HTML/CSS/JS ──HTTP──▶ Spring Security (session + CSRF, USER/ADMIN roles)
                              │
                              ▼
                     REST Controllers /api/...
                              │
                              ▼
                     Services (rules, visibility)
                              │
                              ▼
        JPA Repositories ──▶ H2 (local) / PostgreSQL (prod) · Flyway
                              │
                              └──▶ RAWG (metadata) · GG.deals (prices)
```

## Technical decisions

### Security on the server, not the UI

The frontend **never decides permissions on its own**. Without a login, protected routes return `401`. A regular user trying to add a game gets `403`, and so does any write without a CSRF token. Unknown fields are rejected, such as `role` on sign-up and `userId` in the diary, so nobody can escalate privileges through the request body.

### Predictable error contract

Invalid input returns `400`, a missing resource `404`, a conflict (e.g. a duplicate username) `409`, and a successful creation `201`. User entities are never serialized: the API only exposes a view with ID, username, name and role.

### Resilient imports

Batch imports save their progress and can be paused and resumed without creating duplicates. Genres are mapped to Portuguese, and uncertain Steam App ID matches are left blank for manual review instead of risking a wrong link.

### Two databases, one schema

H2 runs locally with zero setup and PostgreSQL runs in production, both versioned with **Flyway**. The project also ships a data migration tool between them.
