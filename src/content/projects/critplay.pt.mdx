## O projeto

O **CritPlay** é uma comunidade de jogos: você registra o que está jogando, dá notas, publica resenhas, segue outras pessoas e descobre o que jogar em seguida. O backend Java e a interface web rodam na mesma aplicação, e a demo está publicada em [critplay.vercel.app](https://critplay.vercel.app).

## Funcionalidades

- **Catálogo** com busca e filtros, edição administrativa e importação da **API RAWG**, individual ou em lotes de 500, 1.000 e 2.000 jogos
- **Diário** com progresso, notas de meia estrela (0,5 a 5), resenha e datas, além de biblioteca por status, favoritos, desejos e listas
- **Social:** perfil com avatar e banner (inclusive GIF), até quatro jogos em destaque, seguidores, amizades, **feed de atividades** e curtidas em resenhas
- **Preços de PC** via API do GG.deals
- **Administração:** contas e papéis, suspensão, denúncias, moderação de resenhas, bloqueios e limpeza de imagens sem uso
- Login por sessão, troca de senha e recuperação por e-mail (SMTP ou Resend)

## Arquitetura

Monólito modular: interface estática e API REST no mesmo processo Java.

```text
HTML/CSS/JS ──HTTP──▶ Spring Security (sessão + CSRF, papéis USER/ADMIN)
                              │
                              ▼
                     Controllers REST /api/...
                              │
                              ▼
                     Services (regras, visibilidade)
                              │
                              ▼
        Repositories JPA ──▶ H2 (local) / PostgreSQL (produção) · Flyway
                              │
                              └──▶ RAWG (metadados) · GG.deals (preços)
```

## Decisões técnicas

### Segurança no servidor, não na interface

O frontend **nunca decide permissões sozinho**. Sem login, rotas protegidas retornam `401`. Um usuário comum tentando cadastrar um jogo recebe `403`, e qualquer escrita sem token CSRF também. Campos desconhecidos são recusados, como `role` no cadastro e `userId` no diário, o que evita que alguém escale privilégios pelo corpo da requisição.

### Contrato de erros previsível

Validação inválida retorna `400`, recurso inexistente `404`, conflito (por exemplo, usuário duplicado) `409` e criação `201`. Entidades de usuário nunca são serializadas: a API expõe apenas uma view com ID, username, nome e papel.

### Importação resiliente

A importação em lote salva o progresso e permite pausar e retomar, evitando duplicatas. Os gêneros são mapeados para português, e correspondências incertas de Steam App ID ficam em branco para revisão manual, em vez de arriscar um vínculo errado.

### Dois bancos, um esquema

H2 para rodar localmente sem instalar nada e PostgreSQL em produção, os dois versionados com **Flyway**. O projeto inclui uma ferramenta de migração de dados entre eles.
